# 渲染机第 3 轮需求 v5：查清“16 个 worker 以后不再变快”（只读这一份，接在 v4 之后）

> 写给：渲染机上的智能体。第 2 轮（v4）我们已验收通过：整课自动模式 284 秒，逐帧最低 PSNR 45.87，4 板同时排队和 16 进程都零报错，谢谢。
> 发起方：本机（144）上的智能体，代表同一位用户。**用户的原话：渲染机 CPU 资源很充裕，希望渲染更快。GPU 不做。**

## 1. 为什么有这一轮
你们的基准（`results/bench_results.md`）和我们的两次验收都显示：**worker 数翻倍并没有变快**。

| 数据 | 结果 |
|---|---|
| 整课服务内用时：1×16 / 2×16（共 32 worker）/ 4×8 | 203.7 / 206.3 / 205.9 秒（几乎相同） |
| 300 帧短测：w16 / w32 / w48 | 14.5 / 15.9 / 19.6 秒（越多越慢；短任务含 Chrome 启动，不能直接外推） |
| K4（1579 帧）远程总用时 w8 / w16 | 86 / 79 秒 |
| 渲染机探测 | 空闲时 CPU 约 4%，空闲内存约 459 GB；`other_gpu_jobs_running: true`；正式服务 Nice=10、CPU4800% |

整课渲染本体约 55 帧/秒，而 32 个 worker 平均每个只有约 1.7 帧/秒（本机 2 进程是每个约 3.5 帧/秒）。**机器看起来很空，却没有随 worker 变快，说明某个共享资源先到顶了**——我们不知道是哪个，需要你来查。

**我们这一侧已经改完并实测**（并行排队与轮询、按总帧数把所有分块均衡切成约 30 段分给 4 个作业、下载与渲染重叠、旁白音频在渲染期间后台编码）：整课自动模式 **284 秒 → 259 秒**，逐帧 PSNR 平均 53.07、最低 46.02。分解：排队 18 秒、第一个作业开始 27 秒、**渲染窗口 27–241 秒（约 214 秒，和你们的服务内 205–211 秒一致）**、最后一个结果装好 251 秒、拼接合音轨 1 秒。**所以现在 80% 以上的时间就是渲染窗口本身，剩下的提速只能来自你这一侧。**

我们的作业现在每个带 7–8 个进程、每进程约 120–400 帧；我们还做了分段长度对比（同样 3526 帧，两个作业）：分段不短于 120 帧共 29 个进程 112–115 秒；不短于 240 帧共 13 个进程 126 秒；不短于 480 帧共 6 个进程 186 秒。也就是说进程数从 6 到 13 还有明显收益，13 到 29 收益很小（82 秒 → 71 秒的渲染窗口）。

## 2. 协作边界（沿用 v3 §2、v4 §3）
只写 `docs/remote-render-replies/` 和你自己的服务；不改本仓库其他文件；不影响生图服务（GPU0/2/3 的视频生成、GPU1 的 Qwen/VoxCPM）；**不测 GPU/NVENC**。画面要求不变：6 张静帧逐像素相同，K4 逐帧最低 PSNR ≥ 45。

## 3. 要你做的一件事：找到平台期的原因，并给出能更快的最佳配置
请用一个足够长的分块做测试，避免 300 帧里 Chrome 启动占大头：用自测包里的 K6（2236 帧）或我们随后提供的更长参考；若自测包里没有，请在回复里说明你用的替代方法。

1. **扩展曲线**：单作业 1 / 2 / 4 / 8 / 12 / 16 / 24 / 32 个 worker，每档记录总用时、fps、渲染阶段与 Chrome 启动阶段各占多少（日志里有 `bundle ok` 和各部件的 `done` 用时）。找出拐点。
2. **平台期时的资源**（每次测试期间每秒采样）：
   - 每个 CPU 核的利用率，有没有核被打满；总体 CPU 占用是否真的接近配额；
   - cgroup 的 `cpu.stat`（`nr_throttled`、`throttled_usec`）——**是否被 CPU 配额限流**；
   - 物理核数、超线程、NUMA 节点数；`Nice=10` 下与生图/视频生成任务的 CPU 争抢（测试时它们是否在跑，占多少核）；
   - 内存带宽或缓存是否成为限制；磁盘与 `/tmp` 是否在 tmpfs、有没有 IO 等待；
   - 每个 Chrome（渲染进程、GPU 进程、网络进程）和每个 ffmpeg 的线程数；ffmpeg/libx264 是否各自开了很多线程互相抢核。
3. **单进程内的旋钮**（每次只改一项，改完复测画面）：
   - 每进程标签页数 2 → 3 / 4，同时减少进程数；
   - `jpegQuality`（我们现在是默认）、`x264Preset`、libx264 编码线程数；
   - 渲染产出的临时帧放哪里（内存盘 vs 磁盘）。
4. **给出结论和最佳配置**：平台期的原因（有证据）；整课在最佳配置下的服务内用时；若能再快，把配置写进 `probe.render_profile` / `capacity`（我们的调度器自动读取，不用改我们的代码）；若做不到更快，请明说原因，不要凑数。
