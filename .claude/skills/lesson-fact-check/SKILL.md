# 做课事实核对

本项目的代码输出都是真实运行的，但**文字断言没有人查**。真实教训（都已发生过）：
- 第 43 课脚本初稿写“两处不一样：挂号一行、叫号一行”，实测 diff 是三行（挂号、看排队、叫号）；
- 写“长大就是搬家”，第 22 课原话是“有时原地变大，有时搬到新的地方”；
- 计划里写“九条命令”，实际是八句。

核心做法：**只挑少数真正影响可信度的断言，逐条查证**，不做全文审计。上游方法来自 OpenMAIC 的 fact-check（原文见 `references/upstream-fact-check.md`，那里引用的读页面、搜索、提问工具是它自己运行时的，本项目没有）。

## 什么时候跑
1. **脚本阶段**：`build_script.py` 跑通、通俗度统计过关之后，**请用户说“脚本通过”之前**。此时脚本未批准，发现明确错误可以直接改，并在回复里说明改了什么。
2. **发布阶段**：写 `publish_prep.py` 的简介、`make_exercises.py` 的课后练习之前与之后各看一遍。
3. 用户说“核对事实 / 查一下说法对不对”时。

## 读什么
本课 `artifacts/script.json` 的每段旁白；`script-review.html` 里的板书文字（`build_script.py` 的 `BOARD`）；`publish_meta.json` 的简介；`exports/metadata/exercises.txt`。

## 第一步：挑高风险断言（静默列清单，不逐句查）
- 数字、个数、时长、次数（“八句命令”“十行”“容量翻一倍”）；
- diff 报告原文（`5,6c5,6`）、编译器提醒与报错原文、退出码、`-O0/-O2` 说法；
- 引用的来源原话（cppreference、gcc、diffutils、Wikipedia）；
- “总是 / 只有 / 一定 / 永远”等绝对化说法，因果句（“因为……所以……”）；
- **对前面课的回扣**（“第 22 课说过……”“第 23 课找人每次扔掉一半”）；
- 同一课里前后矛盾；
- 板书、旁白、简介、练习三处说法不一致。

正确的内容、措辞偏好、无害的简化、琐碎细节一律跳过。

## 第二步：只查清单上的，按类型找证据
| 断言类型 | 去哪里查 |
|---|---|
| 本课输出、diff、提醒、退出码 | `projects/<课程>/validation/*.txt`（`grep` 原文，注意 -O0/-O2、三套选项） |
| 回扣前面课的说法 | 那一课的 `projects/<课程>/artifacts/script.json`（用 python 或 `grep` 找原话，对到字） |
| 引用来源原话 | 已打开原页的来源（WebFetch 取原页），不是搜索摘要；只引原话，不转述成页面没说的话 |
| gcc / diffutils 行为 | 本机 gcc 13.3、GNU diffutils 3.10 实跑；别的版本只说“可能不同” |
| 规则或语言标准 | cppreference 等语言参考原页 |

要点：
- 一条一条查；复合句只查有疑问的那一半；一般一轮不超过 6–8 次搜索；**不猜网址**，只取用户给的或搜索返回的页面。
- **本课程自己的内容不能证明自己**：脚本里的话要拿 validation 或来源去对，不是拿另一段旁白去对。
- **不运行未定义行为来“验证”**（沿用系列约束）；只引原文。
- 搜索摘要只能标 anecdotal，不能当证据（与 `research_brief` 的 reliability 规则一致）。

## 第三步：判定
- 查到明确证据 → 明确错误或不严谨；
- 查不到可靠证据 → 写“需核实”，**不要写成错误**，也不要编一个更正；
- 有版本、日期、编译器差异 → 写明条件（“本机 gcc 13.3”）。

## 第四步：报告（保存到 `projects/<课程>/validation/fact-check.md`，并在回复里给出摘要）
一般 3–8 条，没有就少；没有重大问题时写“扫描范围：……；未发现明显错误”，不要说“完全准确”。分三组（空组省略），条目全局连续编号：

- **A. 明确事实错误**
- **B. 表述不严谨**
- **C. 需要核实**（只放确实重要的）

每条先一行粗体：`**1. s7｜diff 行数｜数错**`，下面固定三条，每条一两句：
- **原始表述：** 只引相关片段；
- **存在问题：** 说明错在哪、正确事实是什么，必要时附来源与日期；
- **修改建议：** 只写改法或替换句，不重复引用前面已写的内容。

不写分数、置信度、冗长的方法说明、正确的断言、小的风格问题。

## 第五步：已批准的输入不静默改
计划、提案、**已批准的脚本**、用户给的材料都是已批准输入。如果核对发现它们本身有错：
- 不要直接改，也不要悄悄覆盖；
- 在回复里列出位置、证据，给三个选项：全部改、只改已确认的错误、保留不改（附报告）；
- 已批准的脚本一旦改旁白，要重算时长，并且可能要重配音——先把代价告诉用户。

## 和现有检查的关系
`build_script.py` 的难词表、数字统计、`claim_check` 检查的是**形式**（有没有英文、数字、难词）；本 skill 查的是**内容对不对**。两者都要做。

## 完成标准
- 清单只含高风险断言，没有为凑数而查琐事；
- 每个结论都有证据位置（文件与行、来源页）；
- 报告已保存，回复里给了摘要与要用户决定的事；
- 没有改动任何已批准的内容而没有告诉用户。
