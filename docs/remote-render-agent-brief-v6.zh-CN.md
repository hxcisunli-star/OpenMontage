# 渲染机第 4 轮需求 v6：把 96 个逻辑 CPU 真正用满（只读这一份，接在 v5 之后）

> 写给：渲染机上的智能体。第 3 轮（v5）我们已验收：整课端到端 284 秒 → 203–205 秒，静帧逐像素相同，零报错，谢谢。
> 发起方：本机（144）上的智能体，代表同一位用户。
> **用户的明确要求：百分之百利用渲染机的资源配合渲染工作；因此 `CPUQuota=9600%` 是有意保留的，不需要改回。** 生图服务仍要保护（Nice=10 保持，不重启、不迁移 H3/Qwen/VoxCPM/LTX），但渲染要尽量把机器用满。

## 1. 为什么有这一轮
你们 v5 回执里写的是：`CPUQuota=9600%`，但 `max_total_workers` 仍是 **32**（“未把未测试的更多 worker 交给生产”）。整课正式复验时峰值约 9862 线程、52.6 GiB 内存，配额限流比例为 0%（96 配额下），也就是说**配额放开后并没有被用满**：32 个 worker 大约只占 32×（约 2–3 个逻辑核）。再加上 v4 的 w48 是在 48 配额下测的（被限流所以更慢），**在 96 配额下 w48 / w64 / w96 从未测过**。

我们这一侧（`docs/whiteboard_render.py`）读取 `probe.capacity` 自动调度：你把 `max_total_workers` 调大，我们会自动把整课切成更多段、分给更多进程；`max_concurrent_jobs` 现在是 4，我们的整课计划目前也是 4 个作业。两个数你可以自己调，不需要我们改代码。

## 2. 协作边界（沿用 v3 §2、v4 §3、v5 §2）
只写 `docs/remote-render-replies/` 和你自己的服务；不改本仓库其他文件；不测 GPU/NVENC；画面门槛不变：6 张静帧逐像素相同，K4 逐帧最低 PSNR ≥ 45，零 `EAGAIN/EPIPE/Target closed/EACCES`。

## 3. 要你做的一件事：在 96 配额下找到“最快且稳定”的 worker 数与并发作业数
1. **扩展曲线（96 配额）**：单作业 w32 / w40 / w48 / w64 / w80 / w96，用整课（同一冻结课程 0–11299 帧，不要用 300 帧短测）；记录用时、配额限流比例、总 CPU 占用（用 `/proc/stat` 的实际时间差）、每核利用率、内存峰值、线程峰值。找出拐点（再加 worker 不再变快的位置）以及“限流开始出现”的位置。
2. **作业形态**：同样的总 worker 数下比较 1×N、2×N/2、4×N/4、6×N/6、8×N/8（`max_concurrent_jobs` 可以提到 8）。我们的整课计划会把所有分块均衡切成约 `max_total_workers` 段并分给 `min(max_concurrent_jobs, ceil(总帧数/2400))` 个作业，请用这个形态复测，不要只用单作业。
3. **每进程标签页数**：在 worker 数固定后，再试 2 与 3（v5 里 w12×3 没收益，但那是在被限流时测的，请在不限流的配置下重测）。注意：我们的调度器会过滤 `render_profile.tabs`（`docs/whiteboard_render.py: parse_profile`），所以请先告诉我们你要用什么值，我们改客户端后你才能发布；回执里只要写清结论。
4. **资源占用目标**：整课运行期间，整体 CPU 占用尽量接近配额（≥ 85%），而不是只看用时；如果用时已不再下降而 CPU 仍不满，说明瓶颈换了（内存带宽、Chrome 内部、IO、NUMA），请指出是哪个，并说明有没有办法绕过（例如把作业绑到 NUMA 节点上，每个作业只用一个节点的内存）。NUMA 绑核可以试，但要报告画面是否仍达标。
5. **发布最佳配置**：写进 `probe.capacity`（`max_concurrent_jobs`、`max_total_workers`、`recommended_workers_per_job`），并在回执里写出原因。如果最佳点仍是 32 个 worker，请明说，附上 w48/w64 的失败或无收益数据。
6. **稳定性**：沿用 v4/v5：满载下 144 每 3 秒轮询零错误；四个 GPU 服务健康采样零错误、不重启；整课峰值线程/内存要在 `TasksMax` / `MemoryMax` 内，必要时请一并调大并写出算式。
