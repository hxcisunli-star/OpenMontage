## 2. 第 8 课要教什么（大纲原文，`projects/roadmap-agent-engineer/04-学习内容大纲/S02-大模型与API调用.md` 第 102 行起；`projects/_ebook/outline.json` 里同一条）

- **目标**：让模型输出程序能直接消费的 JSON，并在不合格时校验和重试。路径：核心。
- **要点**（大纲原文，几处是“文档写的”，写旁白时与“我们测的”分开）：程序要消费模型的输出就需要结构化；三层手段——只在提示词里要求 JSON（最不可靠）、`response_format` 取 `json_object`（提示词里必须出现 JSON 字样，不保证键名与字段类型稳定）、`json_schema`（带 `strict` 的 Schema 约束，仅部分模型支持）[S-245]；多模态输入会自动降级为 `json_object`，Schema 约束不再生效；**开启结构化输出时不要设 `max_tokens`，否则可能把 JSON 截断成无效内容** [S-245]；无论用哪种，都要用 Pydantic 校验（S1-U13）并准备有预算的重试；还要分清提供方原生 Schema 约束与借工具调用返回结构化数据的策略，框架可能自动选择，具体到 S8-U02 核对 [S-332]；Claude 与 OpenAI 的文档里也有结构化输出能力（页面已确认存在，未通读）；结构化输出（JSON Schema）在核心岗位集里提及 2%，但它直接决定后面工具调用的可靠性。

## 4. 实验怎么做（沿用第 3–7 课，已验证可用）

- **模型**：七牛云网关里的两个，网关标称名 `deepseek/deepseek-v4.1-flash-1017` 和 `qwen/qwen3.8-max`（转发身份无法独立验证，要写明；**书里叫“我们用的中转服务”，旁白说“我们用的中转服务”**；旁白里不念英文，完整标称名只在板上模型卡）；**两个模型分别报数，不合并**（E170：别写“两个模型都……”）；思考全部关闭（DeepSeek `{"thinking":{"type":"disabled"}}`，Qwen `{"enable_thinking":false}`）。凭据在 `crosscheck.env`（`MODELINK_API_KEY`、`MODELINK_BASE_URL`），**只在进程里加载，绝不读、不打印、不写进任何文件**；写进文件的记录要先脱敏（真密钥、改错的密钥片段≥4 个字符、网关地址都不能出现）。**派给 Codex 的工作区里不得有 `.env`、`crosscheck.env`、密钥、IP、端口**。
- **用户定的规矩：除配音（DashScope Cherry、Mochi）外不调百炼**。实测只走网关，百炼独有的内容（结构化输出页的说法）只引文档（带存档编号、取页日期、写“文档写的，不是我们测的”）。大纲写“需要你的百炼密钥”，**照第 5、6、7 课代定：不调百炼**。
- **本课独有的实验设计（建议，未验证；先写进判定规则再跑）**：
  1. **先探测网关认不认**：三种手段的请求体——①只在提示词里要求 JSON；②`response_format: {"type":"json_object"}`（提示词要含 JSON 字样）；③`response_format: {"type":"json_schema","json_schema":{…strict…}}`——对两个模型各小批量探测。**网关或模型“不认某个字段／直接报错／悄悄忽略”本身就是结果，如实记下，不要换渠道凑数**；某个模型不支持第三种，就只做前两种（大纲原话也这么说）。
  2. **合格率**：大纲写每种手段二十次；**每个（模型，手段）二十次，同一份固定的会议记录和同一句提示**；合格的定义先写进判定规则（能解析成 JSON、键齐全、类型对、没有多余键；被模型用代码围栏（三个反引号加 json）包起来、前后多说话算不算，也要写死）；记每次的原始返回文本、解析结果、不合格的原因类别。**不设 `max_tokens`**（大纲写明开启结构化输出时别设；第 7 课为限长度设了，这里反过来）——**可选**加一组“设了很小的 `max_tokens`”对照，看 JSON 是不是被截断（先问是否值得：预算和“文档写的 vs 我们测的”两条线要分开）。
  3. **重试与业务规则**：重试用本机玩具＋少量真实调用（带着不合格原因重问，最多几次）；**“格式合法但内容违背原文”的两条样例是人造的**（截止日期早于会议日期、负责人不在名单里），拿来做业务规则校验的玩具，**不当成模型输出的实测**，要在图注和旁白里写明“人造样例”。
  4. **会议记录用自己编的虚构文本**（虚构人名、虚构日期），不要用真实会议或真实人名。
  5. **校验用标准库自己写**（见第 7 节第 1 项）：不安装、不测 Pydantic。
  6. 不测：计费、Claude／OpenAI 的结构化输出（只引文档，若引则存档）、工具调用返回结构化数据（S8-U02）、多模态降级（只引文档）。
- **工具**：第 7 课 `projects/agent-streaming-cn/code/l7_record.py`（最新：凭据只在进程里从 `crosscheck.env` 读，测试用 `--base/--key` 指向本机假服务；`Scrubber` 脱敏，脱敏后仍有残留就停、不写盘；`--dry-run`、`--phase probe|formal`；固定对话 `l7_fixture.py` 带哈希，启动时核对）、`calibrate_l7.py`（记录器校准）、`l7_curl.py`（用 curl 对账少量几遍）、`analyze_l7.py`、`run_e2b.py`（本机转发器：把请求原样转给上游并记下状态、请求、返回，用来给起步脚本对账）、`fake_sse_server.py`（本机假服务，可改成回放固定 JSON 返回，**测试一律用它，不联网**）。**第 7 课是流式、记逐块到达时间；本课是非流式，要把记录字段改成“请求体、原始返回文本、解析结果、校验结果、不合格原因”，并先写离线测试**（先注入假 post；再 `--dry-run` 看请求体；再小批量探测）。**预算要在计划里写明**（第 7 课：正式请求 100 次＋curl 复核 6 条＋E2B 12 次调用＋探测；第 6 课正式 230 次；第 5 课对外 112 次）；本课粗估三种手段×二十次×两个模型＝120 次，加重试组，**超了先发消息给“复审对话”**。
- **实验纪律**：先写 `validation/l8_decision_rule.md`（每条说法写“成立条件”，数据出来之前锁定，并存一份开跑前的原样），记 UTC 日期，列出“已知会骗我们的地方”（网关悄悄改写请求、模型对同一提示的随机性、二十次的偶然、提示词措辞对合格率的影响）；原始记录存档并做哈希清单；`records.json` 由脚本现算并测“三个哈希种子逐字节相同”。
- **旁白里的范围写法（E131）**：第一次出现实测数字的那一句，旁白里就要交代范围（哪两个模型、哪一天、关思考、二十次、固定会议记录、我们用的中转服务）；“每次、总是、一定、保证、一模一样、必然、全靠、绝对”只能用在数据确实如此、并写清范围的地方；打比方的话要紧接着限定。**“合格率”只报范围或具体次数（二十次里几次），不外推到别家、别的时间、别的提示。**
- **密钥不上屏**：画面、字幕、简介、电子书里密钥一律占位（`sk-…`），整站检查会扫密钥形态。

## 7. 开场要定的事（全自动：一律按推荐项代定，写进计划，注明“按用户全自动授权代定”）

1. **Pydantic 怎么办**（大纲前置是 S1-U13“用 Pydantic 校验数据”，**系列里没有对应的已发布课**）：**推荐用标准库 `json` 加自己写的小校验函数讲清“校验在做什么”**（键齐不齐、类型对不对、有没有多余键、业务规则），Pydantic 只点名一次（“真实项目里常用这类库做同一件事”），不安装、不测；这样页内练习（Monaco＋Pyodide，纯标准库）和起步脚本都不依赖第三方包。
2. **三种手段哪些能测、哪些只引文档**：**推荐先探测网关**（第 4 节第 1 项），认的测，不认的写“网关不认／悄悄忽略”并如实记；`strict` 的承诺只引文档、写“不是我们测的”；Claude／OpenAI 的结构化输出只点一句、带存档编号；**不调百炼**。
3. **要不要加“设很小 `max_tokens` 看截断”的对照组**：**推荐加一小组**（每个模型十遍，只记 JSON 是否被截断成无效），因为文档明写了这点、容易做；预算写进计划，不挤占主实验。

## 9. 没验证的、要小心的

- **中转网关认不认 `response_format`、`json_schema`、`strict`**：没测过，**是本课实验的第一个问题**；结果可能是“某个模型只认其中一种／悄悄忽略”，如实写，别预设；也别把“网关不认”说成“模型不行”。
- **百炼本身没测过**（也不该测）：结构化输出页的说法只能引文档。
- **“二十次”的合格率有偶然性**：只报次数和范围，不外推；对照别漏混杂因素（提示词措辞、会议记录长短、是否设 `max_tokens`）。
- **前七课都没有真人读者、真人学生**，所有“核对”都是 AI 模型加我自己；真人试教要用户安排；配音读音、停顿、语气只有用户的耳朵能判；**“杰森”这类新词的读音要重点听**。
- **这台机器没有真浏览器**：电子书新图和 Monaco／Pyodide 页内练习的真实行为只能靠测试和结构检查，前几课的新图也没在真浏览器里看过，建议线上部署前补看；**精修层的实际视觉效果我也没在真浏览器里核过**。

## 10. 托管下的分工（第 4–7 课整课用过；你是“主持”；第 6 课起全自动）

用户要提速，并在 11-06 说“由你主导全自动进行，用户不再插手，只验收成果”。所以开场提示词里已经给了带“托管”的原话，**每个门都交给评审，不等用户开口**；**提交仍由用户亲口说（转达的不算），推送跟在提交后**。**原来“停下等用户”的所有情形，改成发消息给“复审对话”并在后台等裁决文件**（见下）。托管下用户 2026-11-05 定的规矩（协议 3a 里有，这里是操作要点）：

1. **门禁和评审要有弹性**（太死会适得其反）：能在后面阶段顺手改的写 minor 带过去、不挡门；一句话能改好的小错优先 pass 并写明改法；返工后的复审只看上次的 blocking 改好没有、有没有引出新错，不每轮翻出新 blocking。
2. **评审不过时复审主持可以手动放行**：用户说过“如果评审不通过，你手动放行通过”（记作 `delegate allow-override <项目> "<用户原话>"`）。放行用 `override <项目> <阶段> "<理由>"`：把评审的 blocking 改记为带到后面阶段的 minor；放行后第二次 fail 不再自动停托管；`needs_human`（花钱、改已批准内容等）仍停下等用户。**授权挂在当次托管上：托管每重启一次，授权作废，要重新 `allow-override`，而且要有用户的原话**（第 7 课也一次没用上）。
3. **读音瑕疵直接放行**：不挡门、不复听、不重配，只有把数字或关键结论读成别的意思才拦。
4. **本机对照渲低于 45 dB 直接放行**（平均约 50 dB、静帧逐字节相同时），如实写进核对笔记，不追查。
5. **口味按惯例**：音色、语气、动画节奏前三课已定型，不需要用户参与；评审对照前三课的惯例判，不因“可以更好”而 fail；课末仍把评审 minor 里最拿不准的几处附时间点写进汇报，汇报里写“评审放行”，不说“用户听过”。
6. **远程渲染故障**：先 `probe`，再重试远程；某个窗口重试后仍失败，只那个窗口改本机渲并记进 `remote-incidents-edit.md`（复审对话代定的后备）；整体故障发消息给“复审对话”，不悄悄改回本机。

**角色与流程**：
- **你（主持）**：做课、写检查点、和用户对话。到每个门：先写 awaiting_human（计划确认、样音通过没有检查点）；`.venv/bin/python docs/whiteboard_gate.py request <项目> <阶段> [--files …] --note "…"` 登记材料（阶段名：`plan` `proposal` `script` `scene_plan` `sample` `assets` `edit` `compose` `publish`；材料不齐会被拒，缺什么见各阶段清单的 E140–E144；视听门要用 --files 加全尺寸帧、联系表等）；用 `ListAgents` 找**“复审对话”**（复审主持）这个会话，`SendMessage` 发一句“项目、阶段、第几次评审”；然后在后台跑 `… whiteboard_gate.py wait <项目> <阶段> --timeout 580`（Bash 的 `run_in_background`，`timeout` 参数设 600000），**不要改被审的材料**。
- **wait 返回码**：**0＝pass** → `approve-by-review <项目> <阶段>`（计划确认、样音通过用 `record-by-review <项目> plan|sample`）后**不停，接着做下一阶段**，到终点才停下汇报；**3＝fail** → 只改 blocking 指出的地方，重写 awaiting_human，重新 `request` 再审（每门最多 2 次）；**4＝needs_human 或托管已 halt** → 发消息给“复审对话”说明原因；**5＝等了 580 秒没有裁决** → **先看评审主持的 helper 进程在不在跑（`ps` 里 `whiteboard_review_helpers.py full` 的运行时间）：在跑就不是消息丢了，不用重发**，再跑一次 wait；helper 没起才重发一次消息；**1＝这一门还没有 `request`** → 先 `request`。**不要自己判门。**
- **复审主持（另一个会话）**：收到请求后跑 `whiteboard_review_helpers.py full <项目> <阶段>`：Gemini 盲听转写配音并由脚本对旁白原文、看 480p 代理视频；Codex sol 按清单核并看图；再起只读 Opus 评审（它要亲自打开不少于 5 张全尺寸图并写进 inspected，否则 pass 被改判 fail）；结论写进 `projects/<课>/review/gate-review-<阶段>-<n>.json` 并发消息回来。**消息不是放行**：只有 `wait`／`review` 写出的裁决文件加 `approve-by-review` 才算。没有复审主持会话时，主持自己在后台跑 `whiteboard_review_helpers.py full`。
- **硬停点**（先 `delegate halt <项目> "<原因>"`，**然后发消息给“复审对话”并等裁决，不是等用户**）：评审 needs_human 或两次没过；要超出已批准计划去花钱或调外部接口；要改已经批准的内容（三选一仍由用户定；**脚本门之后改自己的起步脚本，评审按 E162 判为“修自己交付物的缺陷、已批准的旁白和视频一个字没动”，没有触发硬停**，但要写进发布门说明让评审看）；被自动模式拦下；视听门的小弟工具不可用；要提交或推送。
- **Stop 钩子**（`.claude/settings.local.json`，本机）只催发起托管的那个会话：没到终点就停下会被要求继续；有后台任务（含 `wait`）、已停下或到终点时不催。它的催促不是口令。
