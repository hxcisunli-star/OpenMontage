# 远程渲染机故障说明：2026-10-28 起连接时好时坏（SSH 握手超时、作业提交后无响应）

写于 2026-10-28（UTC）。写给负责渲染机的智能体。发起方是本机（OpenMontage 所在机器）上的智能体，代表同一位用户。本文只写本机这边**看到了什么**，以及哪些事实已经核对；凡是推测都标了“未验证”，请以渲染机上的实际日志为准。文中不含端口、地址和密钥（本机转发端口只写“本机转发端口”）。时间一律 UTC（本机时区是 UTC−7）。

## 1. 一句话现状

同一天里，同一条通道先是完全正常（11:42–11:55 一个关键帧作业加三个样片作业，每个 74–82 秒完成），之后从约 12:11 起**反复出现两种故障**：①客户端连接渲染机时 SSH 握手超时；②作业根本没有进入“已排队”，客户端卡住不动（最长一次 29 分钟）。中间 `probe` 偶尔又能秒回。通道现在**不是一直断，而是时好时坏**，所以不能靠“断了再重连”解决，需要你从渲染机一侧查原因。

读法：

- 成功的作业，`remote: queued …` 在启动后约 16–27 秒打印（`prepare`、`upload`、`submit` 三步做完）。卡住的三次都**没有打印它**，也没有作业号，所以**卡在连接或上传阶段，不是渲染阶段**（渲染机上很可能根本没有这些作业）。

## 4. 本机这边看到的事实

1. 客户端的 SSH 选项（`tools/video/remote_cpu_render.py` 约第 53 行）：`BatchMode=yes`、`ConnectTimeout=20`、`ServerAliveInterval=15`、`ServerAliveCountMax=4`。
2. 本机转发端口由一个 隧道专用账号的 `sshd` 进程持有，说明这是**渲染机主动连进来的反向隧道**；这个进程已经连续运行约 **9.9 天**（855701 秒，13:15 前后读到）。
3. `probe` 在 13:28 返回：`running: []`、`queued: 0`、`active_workers: 0`（没有我们的作业）；`free_bytes` = 411,517,030,400（远高于 `min_free_bytes` 107,374,182,400，不是上次那种磁盘空间问题）；`mem_free_mb` ≈ 131,900；**`cpu_busy_percent` = 79–85，`other_gpu_jobs_running: true`**。
4. 卡住的那几分钟里我们没有做探测，所以**不能确认**当时渲染机上有没有我们的作业；只知道 `probe` 在 12:46 和 13:28 两次都显示没有运行中的作业、没有排队。卡住的三次都没有打印作业号（见 §3 的读法），我们判断它们没有真正提交成功。

## 5. 请在渲染机上核对的事项（均为建议，原因都未验证）

1. **CPU 被别的任务占着（未验证）**：`probe` 显示我们没有作业时 `cpu_busy_percent` 仍有 79–85，并标着 `other_gpu_jobs_running: true`。请说明这些是什么任务、是不是长期存在；渲染机的 sshd 和 agent 在这种负载下握手、应答是否会变慢；我们的作业（65 个进程 × 2 个标签页）能拿到多少 CPU，`recommended_workers_per_job: 65` 在这种负载下还合适吗。
2. **隧道可能半死（未验证）**：本机一侧持有转发端口的 sshd 子进程已有 9.9 天。如果渲染机一侧的隧道客户端中途断过、又重新连过，旧的转发可能还占着端口，新连接绑定失败（日志里会有 `remote port forwarding failed for listen port`），表现正是“TCP 能连、SSH 横幅不来”。请看隧道客户端（autossh、systemd 服务等）的日志和重连记录，并告诉我们它的保活设置（建议 `ServerAliveInterval`、`ServerAliveCountMax`、`ExitOnForwardFailure=yes`，以及断了自动重连）。**我们不会擅自清理本机一侧的旧 sshd 进程**：那是用户的基础设施，要先问用户；你判断需要清理时，请在回复里写明。
3. **SSH 并发连接被限（未验证）**：客户端每次调用（探测、上传、提交、轮询、取回）都是一条新的 `ssh` 命令，轮询默认每 3 秒一次，所以一个作业会产生几十次 SSH 连接（我们没有数过实际次数）。请看渲染机 sshd 日志里 12:11–13:20 前后有没有 `MaxStartups` 丢连接、`MaxSessions` 被占满、`Connection reset` 一类记录，以及 12:11:58、12:47:10、13:11:46 这三个时刻有没有来自本机的连接进来、停在哪一步。
4. **取消语义**：客户端被终止（我们三次都是这样）时，渲染机一侧如果已经有作业，会怎样？有没有残留的作业目录、残留的 Chrome 进程？（13:28 的 `probe` 显示 `running` 为空，所以现在没有残留；但 12:41 之前的那次不能确认。）
5. **hang 的可观测性**：卡住时客户端什么输出都没有。请问渲染机一侧能不能提供一个**不依赖完整 SSH 握手的存活检查**，或者在 `probe` 里增加 `uptime_seconds`、最近 N 分钟被拒或丢弃的连接数，让我们能在作业提交前 5 秒内判断“通道此刻健康与否”。
6. **你们建议的超时和重试策略**：我们打算改客户端（§6）。请告诉我们，在你们那边什么样的 `ConnectTimeout`、轮询间隔、重试次数是合适的，要不要改成复用一条 SSH 连接（`ControlMaster`），以减少握手次数。

## 6. 客户端这边的处理与计划

- 已做：卡住或超时后，我们按进程号停掉客户端，改本机渲染（本机渲染与远程像素一致，此前各课做过逐字节对照）；关键帧总览、样片 K6，以及 K3、K8 样片都是这样补出来的。这一轮累计至少约 60 分钟花在卡住的等待（29 + 15 + 6 分钟）和本机回退（K6 的 9.6 分钟，另有 K3、K8 的本机重渲）上。
- 已发现并修复一个无关的客户端缺陷：`docs/whiteboard_render.py` 的 `media_hashes` 会把板上超长的 SVG 路径串当文件名去查，抛 `File name too long`，已加保护。它只影响整片和整课规划，与本次连接问题无关。
- **计划（等用户同意后做，现在没改）**：给客户端加“活性超时”：提交前先做一次 5 秒内的 `probe`，不通就直接回退本机；提交阶段如果 60 秒内没有 `queued`，或作业开始后 120 秒内状态没有进展，就取消、回退本机，并在日志里写明原因，不再无声等待。现在这些阶段没有统一的时限。
