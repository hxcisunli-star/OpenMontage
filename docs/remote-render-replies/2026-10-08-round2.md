对应 `docs/remote-render-agent-brief-v4.zh-CN.md`。本轮跨10月7–8日执行。服务已部署，CPU 自测完成；144 项目的代码没有修改。

【授权与约束】用户已确认 CPU 提到32–48核：是。发布CPU配额48核，Nice=10，MemoryMax=96GiB。未测试GPU/NVENC，未停止/重启/迁移H3、Qwen、VoxCPM或LTX。没有新增公网监听，入口仍是144回环 `127.0.0.1:17865`。

【配额】`max_total_workers=32`，`max_concurrent_jobs=4`，`recommended_workers_per_job=8`；每worker 2标签页。48 worker短片测试已通过，但耗时19.60秒，较16-worker的14.49秒更慢，故没有发布48 worker。CPU核配额与worker数量是两个不同限制。

【复测结果】完整表、机器可读结果在 [results/bench_results.md](results/bench_results.md) 与 [results/bench_results.json](results/bench_results.json)。单job×16、2job×16、4job×8的同课首轮分别203.723/206.349/205.940秒，约1.3%的差距不作显著快慢结论。单job×16本次数值最低；发布4×8以支持多分组并行。发布版本完整11300帧复验 **210.545秒**，旧CPU16核/2×8同课对照 **498.581秒**，提速 **2.37倍**。两轮4×8均完成且零进程错误。

六张静帧在16/24/32/48各行均与参考图像素一致。300帧短测最低PSNR：16=48.31、32=47.44、48=46.69dB。24-worker原ceil分块在末尾留下1帧，最后一帧43.88dB，**失败记录保留**；均分为12/13帧后47.83dB。完整课程发布复验的K4参考区间最低 **50.28dB**，SSIM **0.998199**。完整课程的画质数值只覆盖参考包提供的K4 300帧，不能冒称整片逐帧参考对比。

以上是正式service内计算、编码与manifest完成时间，不含上传下载及加音轨。远低于797秒目标，但**不替代144的第17课端到端FULL验收**。本机没有越过协作边界运行会改写课程输出的远端命令。此前144提供的285秒整课验收属于上轮数据，不计作本轮实测。

【进程上限与根因】本机为cgroup v1，真实层级为 `/sys/fs/cgroup/pids/system.slice/openmontage-render-agent.service/`。原TasksMax=2048先于RLIMIT_NPROC=4096达到限制；仅16-worker单job整课就观察到4071线程，4×8首轮8202线程，说明2048甚至临时8192都没有充分余量。原cgroup在重启后旧计数已丢失，不能伪称保存了旧pids.events计数；原错误日志和当时配置仍留档。

已设 `TasksMax=32768`、`LimitNPROC=65536`。预算按测试上限48×每Chrome约300线程×2倍余量=28800，向上取32768；发布32-worker对应19200，仍有余量。父级system.slice的pids.max=max；全局kernel.pid_max=4194304、threads-max=4119892，不是本次先到的上限。Node子工人的真实/proc/limits和cgroup也已核验。Remotion的setpriv用于 `--pdeathsig SIGKILL`，不另降进程限额。证据见 `results/limits-after.json`、`results/actual-worker-limits.json`、`results/limits-final.json`。

【工人故障快速失败】agent监听上传renderer已存在的明确终止行 `worker N failed (exit CODE)`，立即对该job进程组SIGTERM；仍存活则10秒后SIGKILL，终态为failed。主动SIGKILL一个真实Node工人，3秒轮询在3.022秒内观察到failed，错误为 `worker 0 failed (exit null)`。另有自动回归覆盖父进程挂起场景。它不是“3分钟无进展就取消”的看门狗。此次 `om-627606ff6e-k2-1791387081021` 的canceled是本会话保存失败日志后主动cancel，不是144发起，也不是自动超时。旧agent原本会等待父进程退出，确实可能长时间running；本轮已补这个确定失败的收尾。

144维护的render_chunks父进程仍建议正确处理child的error/exit、SIGTERM并以非零码退出；agent补强依赖上述日志协议，不会猜测普通文本Warning就是致命失败。不会把无进展的一般任务擅自取消。现有progress仍是分片进度最大值，判断完成请使用state=completed和manifest，不能只看progress=1。

【满载稳定性】发布版本四job共32worker运行期间，从144通过真实反向SSH每3秒发起一轮status+logs。**69轮 / 138个请求 / 0错误**，覆盖204.0秒；实际发起间隔2.999–3.000秒；关闭自动重试。原始证据 [2026-10-07-round2-poll-pipeline.jsonl](2026-10-07-round2-poll-pipeline.jsonl)，汇总 `results/poll-summary.json`。

新建SSH连接在此网络上需约3–6秒，阻塞式“收到结果再睡3秒”不等于每3秒轮询。连接复用试测仍约4秒，本轮保留了未达定频的两份原始日志，不冒充3秒通过。最终用最多4轮在途的有界重叠请求，按单调时钟每3秒发起，单轮status/logs并行、各自attempts=1；最长返回4.37秒。参考脚本 `results/poll_every_3s.py` 可供144维护者采用，未直接修改你们客户端。

H3/Qwen四个/queue端点共 **1928次成功采样、0次错误**，逐端口延迟详见 `results/health-summary.json`。H3 PID3559317/3559749/3560132，Qwen PID1689662，知识服务PID2520均未变；H3重启次数均0、Qwen既有重启次数1未增加。**可用性未见可测影响；实际生图/视频生成速度影响尚未验证**，因为采样期间队列为空且本轮没有GPU试验窗口，不能将健康检查替代并发生成速度测试。

【webpack缓存告警】已修。根因是job的node_modules指向只读runtime，webpack按它推导.cache位置；Remotion会覆盖webpackOverride.cache。仅对本机v1/v2已安装webpack的默认cacheDirectory添加环境变量入口，每job注入 `OM_RENDER_WEBPACK_CACHE=<job>/work/webpack-cache`。多工人仍由父进程bundle一次。实测每job生成2个pack/index缓存文件，4job生成8个，全部测试日志零EACCES；共享node_modules保持只读，不跨用户共享可写缓存。原文件备份 `.js.om-original`；可复现安装器是本机源码 `remote_render/install_webpack_cache.py`。未来新runtime须运行安装器，结构不匹配会拒绝修改。每个全新job仍需首次打包，未声称消除所有打包耗时。

【probe已更新】agent=openmontage-render-agent/3；capacity和render_profile见 [results/probe.json](results/probe.json)。render_profile为gl=null、headless-shell、tabs=2、hardwareAcceleration=disabled，其余编码字段null，以保持画面。运行时仍om-20261007-remotion-v2，依赖锁完整SHA以probe.json为准。
