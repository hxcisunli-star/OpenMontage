# 白板课网页版（多用户）需求分析

> 状态：草案 v0.1（2026-10-19）。只做研究与需求，不含代码。
> 范围声明：本文不写服务器地址、端口、主机名和任何密钥路径；密钥与 baseurl 由运营方以后提供，不进仓库。
> 数据口径：带“实测”的数字来自本机会话记录与项目文件；带“官方”的来自官方文档（见附录链接）；带“未实测”的是估算或尚未验证，不能当结论用。

## 1. 背景、目标与范围

### 1.1 背景
“老师边讲边画”白板课目前是一套**在 Claude Code 里由人和智能体接力完成**的流程：九道口令门、八个阶段，已做完 43 课。经验沉淀后，流程里确定性的部分已有脚本（口令助手、脚本检查、成片核对、渲染调度等），需要判断的部分靠智能体加人工审阅。

### 1.2 目标
把这条流程做成**多用户网页应用**：用户在网页里创建课程、与智能体对话、逐道门审阅并点击“通过”，最后下载成品包。

### 1.3 已定决策（运营方 2026-10-19 确认）
| 项 | 决定 |
|---|---|
| 模型接入 | 走 API，不走用户套餐登录；密钥和 baseurl 以后提供 |
| 页面服务 | 跑在现有这台服务器上 |
| 渲染 | 继续用远程渲染机，采用排队模式 |
| 用户范围 | 公开注册，人数不定 |
| 学科范围 | 任意学科（不止 C 语言） |
| 费用 | 运营方统一承担，每人每月限额 |
| 交互 | 九道门做成按钮，每一步可对话提修改 |

### 1.4 第一版不做（暂定，见 §9）
手机端制作（只做只读查看）、用户上传自己的 Remotion 代码、视频发布到第三方平台、付费订阅与支付、实时多人协作编辑同一课。

## 2. 现状流程（网页版要承载的东西）

九道门与八个阶段（来源：`docs/whiteboard/lessons-learned.yaml` 的 `stages`、`.claude/rules/whiteboard-protocol.md`）：

| 阶段 | 口令（网页版对应按钮） | 主要产物 | 谁做 |
|---|---|---|---|
| 策划与研究 | 计划确认 | 计划、`research_brief.json` | 智能体研究 + 例子实测，人定题 |
| 提案 | 提案通过 | `proposal_packet.json` | 智能体 |
| 脚本 | 脚本通过 | `script.json`、`script-review.html` | 智能体写，脚本检查自动拦，人审 |
| 场景计划 | 场景计划通过 | `scene_plan.json`、`scene-plan-review.html` | 智能体写板书事件，脚本检查锚点 |
| 素材 | 样音通过 → 素材通过 | 配音、字幕、`asset_manifest.json` | 配音是外部服务调用；人听样音 |
| 剪辑与样片 | 样片通过，开始合成 | `edit_decisions.json`、样片 | 智能体写画面源码，自动检查，人看样片 |
| 合成与核对 | 成片通过，进入发布阶段 | `renders/final.mp4`、核对报告与拼图 | 远程渲染 + 自动核对，人逐张看拼图 |
| 发布与复盘 | 发布通过 | 练习、封面、简介、成品包、复盘 | 智能体 + 脚本，人审 |

**确定性与靠模型的分界（决定网页版哪些走队列、哪些走智能体）**

- 确定性工具（可直接做成后台任务）：`docs/whiteboard_gate.py`（门状态与记录）、`whiteboard_new_lesson.py`（一键建课）、`whiteboard_script_lint.py`、`whiteboard_callbacks.py`、`whiteboard_last_item_check.py`、`whiteboard_thumb_check.py`、`whiteboard_verify.py`、`whiteboard_finish_compose.py`、`whiteboard_render.py`（分块渲染调度）、`whiteboard_wait.py`、`tools/audio/dashscope_tts.py`（配音）、`tools/graphics/dashscope_image.py`（生图）。
- 靠智能体的部分：选题研究与提案、写旁白、写场景事件、**写画面源码**（每课的 `_body_boards.py`、`build_edit.py` 等是智能体复制上一课的脚本再改，单个脚本 40–50 KB 量级，实测）、写练习、复盘。
- 回归保障：`docs/whiteboard_backtest.py`（55 项回测，针对已发布课）可作为网页版工具链的回归套件。

**现状与多用户不兼容的地方**

1. 流程靠智能体“自觉”遵守口令，没有硬拦截（口令助手只能保证阶段对得上，证明不了用户真的说过）。网页版要改成服务器强制。
2. 智能体直接写并执行 Python 脚本、`gcc` 编译运行例子、调用 SSH 渲染通道和配音密钥：单人本机可以，多用户必须隔离。
3. 若干全局状态只服务一个系列：`docs/whiteboard_cover_maker.py` 的 `LESSONS` 表与写死的校徽路径、`docs/whiteboard_release_pack.py` 的固定成品目录、全局词表 `docs/whiteboard/wordlist.yaml`、课间回扣默认在同一系列内。
4. 一部分规则是 C 语言专用（gcc 实测输出、等宽代码板、手写体里不写拉丁字母），“任意学科”要拆成通用包与学科包（§6）。
5. 已有的有利条件：项目根目录可由环境变量 `OPENMONTAGE_PROJECTS_DIR` 指定（`lib/paths.py`），检查点读写走同一路径，因此“每用户一个项目根”不需要改核心库；`lib/checkpoint.py` 的门控强制（`GATE VIOLATION`）可直接复用。

## 3. 可行性结论与约束（研究结果）

### 3.1 模型接入：可行
- 用 **Agent SDK（Python）**：它把 Claude Code 当库使用，每个会话一个子进程，经 `ANTHROPIC_BASE_URL` 与密钥访问模型（官方）。
- `setting_sources=["project"]` 会载入工作目录下的 `CLAUDE.md`、`.claude/rules/*.md` 与 `.claude/skills/`（官方）。所以现有的入口 skill、协议规则、阶段清单、五个教学设计 skill 可以原样放进每个用户的工作目录，不必重写成提示词。技能只能以文件形式存在，SDK 没有程序化注册接口（官方）。
- 可用选项：`cwd`（每用户独立目录）、`max_turns`、`max_budget_usd`（客户端估算，会略超，要留余量）、`allowed_tools`/`disallowed_tools`、`hooks`（`PreToolUse` 可拦截每次工具调用）、`can_use_tool`、`resume`/`session_id`、`include_partial_messages`（流式）、`ResultMessage.model_usage`（每模型的 token 与估算费用，官方说明是估算而非账单）。
- 官方对多租户的要求：每租户独立文件系统，`setting_sources=[]` 或只加载自己的项目设置，`CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`，`CLAUDE_CONFIG_DIR` 指向每租户目录；不要依赖默认选项做隔离。
- **条款**：Agent SDK 适用商业条款，允许用它做面向终端用户的产品；不允许提供 claude.ai 登录或用用户的套餐额度（官方）。品牌：可写“Claude Agent”或“XX Powered by Claude”，不能叫“Claude Code”，产品不得看起来像 Anthropic 的产品。

### 3.2 本服务器资源：够做小规模，不够做大规模（实测 + 估算）
- 4 核、约 7.8 GB 内存（可用约 6 GB）、硬盘可用约 85 GB；Node 18、Python 3.12。
- 官方起步建议每个智能体实例 1 CPU、1 GiB 内存、5 GiB 硬盘，内存随会话变长而增长。粗算，同时活跃的智能体会话 **3–4 个**是上限（估算，未实测），还要给网页服务、数据库、本机 ffmpeg 留余量。
- 已装：FastAPI、uvicorn、watchfiles；没装 Docker；Claude Code 内置沙箱在本机失败（嵌套用户命名空间受限）；`bwrap` 已安装，但能否做进程隔离**未实测**。
- 本机历史上出现过 ffmpeg 内存不足被杀、命令超时的问题，所以本机重活（拼图、响度、静帧提取）必须串行排队。

### 3.3 远程渲染：已有排队能力，可作为共享资源（实测 + 对接说明）
- 渲染机通过强制命令协议访问，客户端 `tools/video/remote_cpu_render.py` 提供 probe、prepare、upload、submit、status、logs、cancel、cleanup、download。
- 渲染机侧支持多作业排队（对接说明中的约定：先进先出、至少 16 个排队、单作业最长 7200 秒；以 `probe` 实时返回的 `capacity` 与 `limits` 为准）。`docs/whiteboard_render.py` 已按 `probe.capacity` 自动切块、并行提交、边渲边下载，并只重渲指纹变化的板（分块缓存）。
- 整课远程渲染实测 **165 / 183 / 202 秒**（第 41 / 42 / 43 课，`render_result.json` 的耗时）；本机回退整课约 27–30 分钟（手册实测）。结论：**多用户下不允许自动回退本机渲染**（会占满应用服务器 4 核，把网页和智能体拖死）。渲染机不可用时应暂停队列并提示。
- 注意：`render_result.json` 里的 backend 是“请求的”而非“实际的”，真实走向要看作业输出里的 `remote timing:` 与 `falling back` 行（既有踩坑记录），队列系统要自己记录实际走向。
- 渲染通道的认证材料只能由服务器的队列进程持有，**不能让智能体看到**。

### 3.4 成本：每课约 9–15 美元量级，但口径粗（实测 + 官方价格）
按本机会话记录，第 41–43 课（均为 Sonnet 5.5）各课从上一课发布到本课发布之间的全部调用：

| 课 | 模型调用 | 输出 token | 缓存读取 | 缓存写入 | 折合美元 |
|---|---|---|---|---|---|
| 41 | 76 | 17.4 万 | 6038 万 | 182 万 | 约 12.3–15.1 |
| 42 | 85 | 15.6 万 | 4172 万 | 126 万 | 约 8.9–10.8 |
| 43 | 139 | 23.0 万 | 5375 万 | 153 万 | 约 11.5–13.8 |

- 价格：Sonnet 5.5 每百万 token——输入 2 美元、输出 10 美元、缓存读 0.10 美元、缓存写 2.50（5 分钟档）/ 4（1 小时档）美元（官方）。区间的两端分别是缓存写入按 5 分钟档与 1 小时档。
- 局限：这些课是在**一个上下文很长的会话里**做的（单次上下文最高约 95 万 token），缓存读取量因此很大；窗口里也混有少量非制作对话。网页版若“每阶段新开会话、只载入该阶段清单”，应当更便宜，**但这一点未实测**，需要 P0 做一课实测。
- 配音（DashScope）与生图的费用**未统计**，需要单独计量（见 FR-COST）。
- 若 baseurl 不是官方 Console 组织的 API，Max/Team 套餐附送的 API 额度不适用。

### 3.5 合规与许可：头号风险，需要运营方确认
1. **模型服务地区**：Anthropic 的支持地区不含中国大陆、香港、澳门（官方支持地区页）；“人身处不支持地区时使用”以及“在不支持地区注册或总部的实体”均不支持；它并明确对通过中转服务转售访问的行为采取措施（官方公告与报道）。因此需要确认：服务器与运营主体所在地、baseurl 的提供方是谁。如果 baseurl 是第三方中转，既有条款风险，也无法用官方额度。
2. **境内面向公众的生成式 AI 服务**：适用《生成式人工智能服务管理暂行办法》；网信办公告显示，调用已备案模型的应用由地方网信办做登记。是否构成“具有舆论属性或社会动员能力”、是否需要备案/登记，**本文不下结论，需要法务确认**（依据为律所解读与网信办公告，未核对条文原文）。
3. **AI 生成内容标识**：《人工智能生成合成内容标识办法》自 2025-09-01 起施行，服务提供者对音频、视频等生成内容要加显式标识，导出下载时保证文件含显式标识，并在元数据加隐式标识（据新华社等转载，未核对原文）。网页版导出的视频与配音若面向境内公众，需要纳入（FR-PUB-4）。
4. **OpenMontage 为 AGPLv3**：改过的版本作为网络服务提供给他人，须向用户提供对应源码。需要明确源码公开方式（例如对用户提供源码链接）。
5. **Remotion**：个人、3 人以内的公司和非营利组织可免费使用；让用户基于你的模板渲染视频是允许的；超出免费范围要买公司许可，其中“提示词到视频工具”类产品对应 Automators 授权，**每次渲染 0.01 美元，每月最低 100 美元**（官方 FAQ）。公开注册的服务是否超出免费范围需要向 Remotion 确认。
6. **其他条款未核实**：DashScope Cherry 音色用于商业服务的条款、字体（ZCOOL 等手写体、等宽字体）的商用许可、用户上传校徽与素材的版权责任、隐私政策与用户数据保存期限。

### 3.6 总体可行性判断
技术上**可行**，工作主要在四处：多用户隔离与服务器强制门控、任务与渲染队列、费用计量与配额、学科泛化。模型层必须做成**可替换**（baseurl 与模型名可配置），以便合规或成本需要时切换提供方；但换模型后技能遵循度与成片质量需要重新验收（未测）。

## 5. 功能需求
每条带编号；“验收”是可检查的条件。优先级：M 必须、S 应该、C 可选。

### 5.1 账号与访问（FR-ACC）
| 编号 | 需求 | 验收 | 优先级 |
|---|---|---|---|
| FR-ACC-1 | 注册、登录、找回密码；邮箱或手机验证（验证方式待定，见 §10） | 未验证账号不能创建课 | M |
| FR-ACC-2 | 注册模式开关：开放 / 邀请码 / 需管理员审核 | 管理员可随时切换，切到审核后新注册账号处于待审 | M |
| FR-ACC-3 | 防滥用：注册与登录限速、验证码、单账号并发限制 | 脚本批量注册被拦下 | M |
| FR-ACC-4 | 用户只能访问自己的系列、课与文件；管理员只读访问需留审计记录 | 越权访问返回 403，且有日志 | M |
| FR-ACC-5 | 账号删除：删除全部课程文件、对话与记录，按期限清理 | 删除后目录不存在、数据库无残留 | S |

### 5.2 系列设置（FR-SER）
一个“系列”相当于现在的“C语言白板课”。
| 编号 | 需求 | 验收 | 优先级 |
|---|---|---|---|
| FR-SER-1 | 系列属性：名称、学科包、授课对象与口吻、配音音色与语言、校徽/标识、封面样式 | 修改后新课使用新设置，已发布的课不变 | M |
| FR-SER-2 | 系列内课程目录与“课间回扣”：回扣只在本系列内查（`whiteboard_callbacks.py` 以系列范围运行） | 引用不存在的课号被拦下 | M |
| FR-SER-3 | 系列词表：通用难词表 + 系列自定义词，替代全局 `wordlist.yaml` | 本系列新词不影响其他系列 | M |
| FR-SER-4 | 校徽/标识上传（图片类型与大小校验、病毒与内容检查） | 非图片或超限被拒绝 | M |

### 5.3 单课工作台（FR-WB）
| 编号 | 需求 | 验收 | 优先级 |
|---|---|---|---|
| FR-WB-1 | 门进度条：展示九道门与当前状态（未开始/进行中/等待你审阅/已通过） | 状态来自服务器门状态，不来自智能体自述 | M |
| FR-WB-2 | 每道门的审阅视图：研究与提案、旁白逐段（可听样音）、场景计划与板书预览、样片播放、成片与核对拼图、发布包预览 | 视图用现有产物生成（如 `script-review.html`、拼图 PNG），内容经净化后在隔离来源内展示 | M |
| FR-WB-3 | “通过”按钮：服务器检查“该阶段处于等待审阅、产物齐全、前序门已通过”才可点击；点击后服务器写检查点并记录（用户、时间、门） | 提前点击被禁用；绕过前端直接调接口返回拒绝 | M |
| FR-WB-4 | 对话修改：每道门内可发消息让智能体修改；修改后重新进入等待审阅；保留历史版本 | 修改前后版本可对比、可回退（沿用 `history/` 归档） | M |
| FR-WB-5 | 已通过内容有错时：给出三个选项（全部改 / 只改已确认的 / 保留），不静默改 | 选择前智能体不改已批准文件 | M |
| FR-WB-6 | 高成本动作二次确认，如“样片通过，开始合成”触发整课渲染并显示预计排队与费用 | 未确认不提交渲染 | M |
| FR-WB-7 | 实时进度：智能体正在做什么、队列位置、渲染进度（SSE 推送） | 刷新页面后状态可恢复 | S |
| FR-WB-8 | 手机端只读查看进度与成片 | 手机浏览器可看，不要求可编辑 | C |

### 5.4 智能体编排（FR-AGENT）
| 编号 | 需求 | 验收 | 优先级 |
|---|---|---|---|
| FR-AGENT-1 | 每个阶段一个智能体会话：载入入口 skill、协议规则与该阶段清单；阶段结束写检查点并停下 | 阶段间不共享长上下文，只通过项目文件交接 | M |
| FR-AGENT-2 | **越门由服务器拦截**：批准记录只能由服务器写入，智能体账号无权写批准记录和检查点的批准字段；用 `PreToolUse` 钩子拦下相关写入 | 智能体试图伪造批准时被拒绝并记录 | M |
| FR-AGENT-3 | 智能体需要的外部能力（配音、生图、渲染、联网检索）都经**服务器提供的工具**调用，由服务器持有密钥和通道；智能体环境里没有任何密钥 | 在智能体沙箱内读不到密钥与渲染通道凭据 | M |
| FR-AGENT-4 | 每次调用限额：`max_turns`、`max_budget_usd`，超出自动停下并通知用户 | 超限后会话终止并写日志 | M |
| FR-AGENT-5 | 画面源码生成方式：第一版沿用“智能体写 Python 脚本并在沙箱里运行”；中期目标是改为智能体只写**声明式数据**（旁白、板书事件、板版面），由固定渲染器执行，减少代码执行面与输出 token | 见 §6.3 | S |
| FR-AGENT-6 | 会话可恢复：服务重启或用户离开后，可用保存的对话记录和项目文件继续 | 重启后继续同一阶段，不重复已完成步骤 | M |
| FR-AGENT-7 | 模型与 baseurl 可配置；按阶段可指定不同模型 | 不改代码即可切换 | M |

### 5.5 任务与渲染队列（FR-QUEUE）
| 编号 | 需求 | 验收 | 优先级 |
|---|---|---|---|
| FR-QUEUE-1 | 本机任务队列（配音批量、核对 ffmpeg、拼图、封面合成、例子编译运行）：并发上限可配，ffmpeg 类默认串行 | 同时提交多个核对任务时依次执行，内存不超限 | M |
| FR-QUEUE-2 | 远程渲染队列：任务类型为静帧、关键帧拼图、样片、整课；优先级 静帧/样片 > 整课 | 样片不被别人的整课长时间挡住 | M |
| FR-QUEUE-3 | 公平性：每用户同时最多 1 个整课渲染；按用户轮转，防止一人占满队列 | 一人连续提交多个整课时其他人仍能排上 | M |
| FR-QUEUE-4 | 显示排队位置、预计开始时间；预计时间按**近期实际耗时**滚动估算，不写死 | 页面可看到位置，渲染开始后显示分块进度 | M |
| FR-QUEUE-5 | 可取消；取消后释放渲染机作业与临时文件（`cancel`、`cleanup`） | 取消后渲染机无遗留作业 | M |
| FR-QUEUE-6 | 渲染机不可用：队列暂停、保留任务、页面提示；**不自动回退本机** | `probe` 失败时任务保持排队，恢复后继续 | M |
| FR-QUEUE-7 | 重试与幂等：沿用分块缓存，仅重渲指纹变化的板；超时与失败有明确原因 | 失败任务可一键重试，且不重复计费 | M |
| FR-QUEUE-8 | 记录**实际**渲染走向（远程/本机）与耗时，不用 `render_result.json` 的请求值 | 日志中有实际走向 | M |
| FR-QUEUE-9 | 本机对照渲染（`local-ref`）等重型验证不对普通用户开放，仅管理员或抽检使用 | 普通用户界面无此入口 | S |
| FR-QUEUE-10 | 队列与任务持久化在数据库，进程重启后恢复 | 重启后排队任务不丢 | M |

### 5.6 例子实测与代码执行（FR-SBX）
课程里的“例子输出、编译提醒”必须来自真实运行（现行规则）。多用户下执行不可信代码：
| 编号 | 需求 | 验收 | 优先级 |
|---|---|---|---|
| FR-SBX-1 | 所有由智能体生成的代码（编译运行例子、画面脚本）在隔离环境里执行：无网络、独立非特权用户、只读系统目录、限制 CPU、内存、进程数、墙钟时间、输出大小 | 恶意死循环/占内存/写系统目录/访问内网均被终止并记录 | M |
| FR-SBX-2 | 隔离方案以 P0 实测结果为准：候选为独立系统用户 + `bwrap` + cgroup 限额（本机已装 `bwrap`，未实测），或安装容器运行时 | P0 给出可复现的隔离验收脚本 | M |

## 6. 任意学科的改造需求

### 6.1 拆分：通用包 + 学科包
| 层 | 内容 | 现状 |
|---|---|---|
| 通用包 | 九道门协议、检查点、队列与渲染、板书写字动画、旁白时长对账、配音与字幕、核对（黑帧、静帧、响度、静默对问答时间线）、封面与发布包 | 已基本通用，但路径和全局表需参数化 |
| 学科包 | 词表与难词规则、板书字形规则、例子核对方式、练习模板、研究来源偏好、回扣规则 | 现在只有 C 语言一套，且与通用规则混在一起 |

C 语言包是第一个学科包，作为参照实现与回归基准（43 课、回测 55 项）。

### 6.2 需要改的点（已核对到文件）
1. `docs/whiteboard_cover_maker.py`：`LESSONS` 全局表与校徽路径写死 → 改为从系列配置读取。
2. `docs/whiteboard_release_pack.py`：固定输出到“C语言白板课_成品” → 改为按系列与用户输出。
3. `docs/whiteboard/wordlist.yaml`：全局单份 → 通用词表 + 系列词表。
4. `docs/whiteboard_lint.py`、`whiteboard_script_lint.py`：C 语言专用规则（等宽里不写中文、手写体不写拉丁字母、旁白无英文与阿拉伯数字）→ 由学科包声明启用哪些规则。
5. 字形：现用手写体缺少 0、o、c、大写与单个拉丁字母，课程通用化后需要覆盖公式、化学式、外语的字体方案，并核对字体商用许可。
6. 语言：旁白目前是中文，配音音色是 Cherry；多语言需要选音色、字数与时长换算（现行 0.238 秒/字只适用于中文）。
7. 例子核对：编程类用实测编译运行；理科需要公式与数值核对（可由计算工具或脚本验算）；文科以事实核对为主（沿用 `lesson-fact-check`），**核对力度因学科不同，要在学科包里写明，不能默认等同**。
8. 脚本路径：大多数脚本以 `projects/<项目>` 作参数，根目录来自文件位置；有 `OPENMONTAGE_PROJECTS_DIR` 可指定每用户项目根。需要逐个核对仍有硬编码相对路径的脚本（回测里就有二十多处）。

### 6.3 画面源码的声明式化（降低成本与风险）
现在每课由智能体改写数十 KB 的 Python 画面脚本，输出 token 多、出错面大、必须执行任意代码。目标形态：智能体只产出声明式的板书数据（板版面、事件、锚点），由固定渲染器解释。这是中期工作，规模大；第一版仍用脚本，但要在沙箱里跑（FR-SBX）。

### 6.4 工作量（相对规模，估计）
| 项 | 相对规模 |
|---|---|
| 路径与全局表参数化 | 小 |
| 学科包机制（规则开关、词表层级） | 中 |
| 第二个学科包的内容与回归课 | 大（每个学科都要做样课并验收） |
| 声明式画面数据 | 大 |
| 多语言配音与时长换算 | 中 |

## 8. 技术方案概要（不含实现细节）

```
浏览器 ── HTTPS ── Web 服务（FastAPI + SSE）
                       │
          ┌────────────┼──────────────────────┐
          │            │                      │
       数据库       门控服务               任务调度器
  （用户/系列/课/    （状态机=检查点      ┌────┴──────────┐
   队列/用量/审计）   + 批准记录）       本机队列      远程渲染队列
                       │                  │                │
                 智能体运行器           配音/核对/        渲染通道客户端
          （Agent SDK，每阶段一个会话，   编译/拼图        （仅服务器持有凭据）
           每用户独立目录与沙箱）
```

- **Web 服务**：FastAPI + SSE。仓库里 `backlot/` 已是同类的只读看板（读检查点、事件文件，SSE 推送），可复用其状态汇总逻辑 `backlot/state.py`；需要加登录、写操作和多租户。
- **数据库**：起步用 SQLite（单机），表结构留好迁移到 PostgreSQL 的余地。存用户、系列、课、任务、队列、用量、审计、对话索引；大文件放磁盘。
- **门控服务**：服务器是门状态的唯一权威。点击“通过”→校验（阶段状态、产物齐全、前序门）→调用既有的检查点写入（`lib/checkpoint.py`、`docs/whiteboard_gate.py` 的校验逻辑）→记录用户与时间。检查点文件仍是磁盘上的事实来源，便于恢复与审计。
- **智能体运行器**：Agent SDK 的 `ClaudeSDKClient`，每阶段一个会话；`cwd` 指向用户项目目录，其中放入产品内置的 skills、规则和阶段清单；外部能力通过服务器提供的工具暴露；`PreToolUse` 钩子拦截越权写入与危险命令。
- **队列**：本机队列与远程渲染队列分开，均持久化；渲染队列包装 `docs/whiteboard_render.py`（保留分块缓存、探测、取消、清理）。
- **审阅视图**：复用现有 `script-review.html`、`scene-plan-review.html`、拼图 PNG 与 `render_report.json`，在隔离来源中展示；视频用范围请求播放。

## 9. 分期与出口条件

| 期 | 内容 | 出口条件 |
|---|---|---|
| P0 验证 | ① baseurl 与密钥能连通，选定模型能跑通 Agent SDK 一个阶段；② 隔离方案可行（`bwrap` 或容器）并通过渗透式验收；③ 按“每阶段新会话”做一课，实测 token 与费用；④ 渲染队列包装验证（多人提交、取消、渲染机不可用）；⑤ 配音/生图/字体的条款核实；⑥ 合规结论 | 六项各有书面结论；成本有实测数 |
| P1 单人网页版（C 语言） | 一个管理员账号：门进度条、审阅视图、通过按钮、对话修改、队列、成品下载、费用计量 | 在网页里完整做出一课，和命令行做出的结果在核对项上一致 |
| P2 邀请制多用户 | 账号、系列设置、隔离、配额、管理后台、监控、备份 | 邀请的少量用户同时使用，无越权、无超额、队列公平 |
| P3 公开注册与多学科 | 注册防滥用、合规标识、学科包机制、第二个学科样课、声明式画面数据（可分批） | 第二学科样课通过同等验收；合规项关闭 |

## 10. 待运营方决定的事项（按影响排序）
1. **地区与合规主体**：服务器、运营主体、主要用户在哪里？baseurl 由谁提供（官方、云厂商、中转）？这决定能否用官方套餐额度、是否需要备案/登记、是否要改用国内模型。
2. **模型选择**：是否接受“模型层可替换”，并在 P0 比较至少两个候选（官方模型 vs 兼容接口的国内模型）。国内兼容接口的技能遵循度与成片质量**未测**。
3. **预算**：单课成本目标、每人每月额度（按课数还是美元）、全站月度上限。
4. **公开注册的防滥用手段**：邮箱还是手机验证，是否需要邀请码或人工审核；内容审核由谁负责。
5. **Remotion 授权**：是否向 Remotion 确认公开服务的授权档位与成本。
6. **学科优先级**：第二个学科做什么，是否愿意先做样课验证。
7. **成品保留期与用户数据政策**。
8. **渲染机容量承诺**：渲染机是否同意被多用户共享，以及对并发与排队的上限要求。

## 11. 验收标准（总）
1. 在网页里由一个新用户从创建系列到下载成品包，走完九道门，成片通过现行的自动核对（`whiteboard_verify.py` 全项）。
2. 越权与越门测试全部失败（智能体不能自批、用户不能访问他人文件、绕过前端不能提前通过）。
3. 渲染机不可用、取消、重启三种异常场景下队列行为符合 FR-QUEUE-5/6/10。
4. 费用报表与服务商账单偏差在约定范围内（范围待定）。
5. 回归：以 C 语言包重做一个已发布课的某一阶段，与既有产物在检查项上一致；`whiteboard_backtest.py` 通过。
6. 合规清单逐项关闭或有书面豁免。
