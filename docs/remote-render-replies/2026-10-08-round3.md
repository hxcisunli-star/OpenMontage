# 渲染机第 3 轮回执（v5，2026-10-08）

【授权与约束】用户已确认：是。GPU/NVENC 未测：是。本轮仅修改本机 CPU 渲染服务及 144 的 `docs/remote-render-replies/`，未改 144 的课程、编排、renderer 或其他项目源码。

**已发布，整课服务内从 205.991 秒降到 144.277/146.820 秒。取较慢一次仍提速 1.40 倍、耗时减少 28.7%。三份完整 MP4 的 SHA256 相同，提速没有改变输出。** 与 v4 的 205–211 秒相比也有明确提升；这不是 144 上传/下载/音频合并后的端到端时间。

【扩展曲线】见 [完整数据表](round3-results/bench_results.md) 与 [JSON 汇总](round3-results/summaries.json)。单作业 w1/2/4/8/12/16/24/32，配额48时为 376.608/219.849/132.758/79.263/61.603/51.526/47.907/50.644 秒。自测包缺独立 K6，替代负载是同冻结课程连续 0–2235 帧。不是用300帧短测推断整课速度。

【平台期的原因】

- **首要原因是 CPU 配额。** 双路 Xeon 8268，共48物理核、96逻辑CPU、2 NUMA节点。4800% 只允许每秒48个CPU秒，不是独占48个物理核。w24/w32分别有59.34%/70.92%的配额周期限流；实际service单秒接近49个逻辑核（采样边界允许短时超过48）。整课48配额限流比例为 81.38%；96配额复验为 0.00%。只提高配额，32-worker长测50.644→37.415秒，整课同条件对照见上。
- **不能把“机器空”直接理解为空闲算力。** 原 `probe.cpu_busy_percent` 使用load average/96近似，现改为`/proc/stat` CPU时间差；长时间没探测时重新取100ms短样本，避免把长空闲区间平均进去。SMT的96线程不等于96个独立物理核。
- **编码线程很多，但本次不是主要限制。** 每个默认FFmpeg最多76线程；显式编码threads=2在实际argv已验证，总线程约11、内存更少，长测却51.526→52.101秒，没有收益，因此不继续threads=4、不发布线程限制。Chrome各主进程/renderer/软件GPU子进程/utility线程数均在每秒原始数据中，w32大致23/25–27/26/11；进程名字含gpu不表示做了GPU生成试验。
- **未发现磁盘瓶颈。** 平台期IO等待平均约0.003%；原scratch、PrivateTmp均是ext4。实际换至`/dev/shm`后52.289秒，未改善，已恢复disk；内存盘私有job目录终态清理已验证。缓存未命中比随并行升高、IPC下降，但仅凭这些不能宣称带宽打满。放宽配额后IMC读写带宽继续升高（约40→55 GiB/s量级），说明40 GiB/s不是本次硬上限；未做独占带宽极限/NUMA绑核实验。
- **生图CPU争抢未出现于本轮。** H3/Qwen队列采样均空，驻留不等于在生成。每秒保存其PID、CPU时间、Nice、线程；各H3/Qwen进程平均远低于0.01核，知识服务约0.02核。渲染服务保持Nice=10；没有为了CPU试验停止、迁移或重启它们。实际GPU生成并发速度仍未测，不能将健康检查说成生图吞吐验收。

【最佳配置】

- `CPUQuota=9600%`，96个逻辑CPU额度；Nice10、MemoryMax96GiB、TasksMax32768、LimitNPROC65536。
- `capacity={"max_concurrent_jobs": 4, "max_total_workers": 32, "recommended_workers_per_job": 8}`。
- `render_profile={"gl": null, "chromeMode": "headless-shell", "tabs": 2, "hardwareAcceleration": "disabled", "videoBitrate": null, "x264Preset": null, "jpegQuality": null, "restartEvery": null}`。
- `runtime_settings={"tmp_mode": "disk", "ffmpeg_threads": "auto"}`。
- 保持现有4job×8worker调度即可自动获得服务配额提升，无需改调用参数或客户端。worker上限仍32，未把未测试的更多worker交给生产。

【probe 已更新】`agent=openmontage-render-agent/4`；`limits.cpu_quota_cores=96.0`为实际cgroup读数。新增runtime_settings帮助核对实际平台配置，load使用实际CPU时间。现有profile、capacity、协议和17865回环入口兼容。见 [发布probe](round3-results/probe.json)、[144满载probe](round3-results/probe-under-load.json)。注意144的`docs/whiteboard_render.py:parse_profile`会过滤tabs；本次继续2页，无需改客户端，未来不能只发布tabs新值就认为客户端已生效。
